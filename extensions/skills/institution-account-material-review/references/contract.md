# 输入约定、产物契约与结论口径

## 一、目录结构

平台在发起执行时把材料物化到目标 AI 员工的 workspace。**默认平铺**：一个材料包一层目录，
不按业务号分子目录 —— 哪些材料属于同一笔业务由你按材料内容判断。

```
/workspace/materials/<材料包>/
├── materials.json          可选。清单（提示业务号 + 每份材料的代号 / 来源文件）
├── S2.json                 单份材料的转写结果（系统录入侧）
├── D1.json                 单份材料的转写结果（客户提交侧）
└── ...
```

`materials.json` 形态：

```json
{
  "pack_id": "PACK-9F2C1A7B0D3E",
  "layout": "flat",
  "note": "hint_business_no 仅由文件名/目录名推测，仅供参考，可能与实际业务不符；…",
  "material_count": 2,
  "businesses": ["B2026001"],
  "materials": [
    {"code": "S2", "hint_business_no": "B2026001", "material_type": null,
     "source_file": "开户录入截图.png"},
    {"code": "D1", "hint_business_no": "B2026001", "material_type": null,
     "source_file": "营业执照.png"}
  ]
}
```

- `hint_business_no` **只是提示**：平台按包内目录名/文件名前缀猜的，可能不准，不要当分笔结论用。
- 同名材料平铺后会撞车，平台会追加 `_2` / `_3` 保证代号唯一（代号是你定位材料的锚点）。
- 缺 `materials.json` 时，按各材料文件里的 `material_type` 推断；代号取文件名。

### 分笔（哪些材料属于同一笔业务）

由**你**判断，判据是材料内容而不是命名：

1. `inspect` 的输出里有 `suggested_groups`（疑似同笔业务的提示：文件名前缀相同，或转写文本里
   出现同一个机构名）—— **只提示不决策**；
2. 结合业务常识确认后，用 `--codes D1,D2,S1` 圈定本轮要核的那笔，`compare` / `verify` 都认这个参数；
3. 分错不影响工具行为（它只是过滤材料集合），但会让「一致 / 不一致」的结论跨业务串味 ——
   所以出表时把本轮 `--codes` 写清楚，人能一眼看出这笔业务由哪几份材料组成。

## 二、单份材料文件格式

```json
{
  "material_code": "D1",
  "material_type": "M-CUST-01",
  "source_file": "营业执照.png",
  "kind": "image",
  "text_lines": ["名称 | 机构开户申请", "统一社会信用代码 | 91350100MA2Y..."],
  "fields": [
    {"key": "name", "value": "机构开户申请", "evidence_quote": "名称 | 机构开户申请",
     "readable": true, "confidence": 0.93, "position": "第 1 行"}
  ],
  "unreadable_regions": [{"desc": "印章覆盖"}]
}
```

- `text_lines` 是**事实层**：平台已完成转写（图片与扫描页走视觉转写，文本类直读）。
  所有取值都必须能在这里原文命中。
- `fields` 是抽取层，可以由 `review.py extract --write` 写入，也可以由你直接补写。
- `value` 为 `null` 或 `readable=false` 表示未读出，按「单边为空」处理，**不要当作不一致**。
- `[[第N页]]`、`[[工作表]]`、`[[印章]]`、`[[视觉要素]]` 开头的行是标记行，不是取值来源。

`extract` 的输出里有两个字段要你留意（都是拿真样例跑出来的，不是设想）：

- `truncated` / `continuation` / `joined_candidate`：值落在行尾、下一行疑似版面换行切出来的续行。
  工具**只提示不自动拼接** —— 版面换行和「下一行是另一个字段」在纯文本里区分不了
  （`姓名 测试` 的下一行就是 `性别 男 民族 汉`），自动拼会造出假值。拼不拼你看着续行内容定。
- `confidence` 被下调到 0.75：说明这个值可能被换行截断，核对表里会带出来。

系统录入侧截图有两个已处理的坑，不用你再操心：一行里塞多个字段时值止于下一个已知标签；
行尾的界面控件文字（样例里是每行结尾的 `AI`）按「同一材料里反复出现的短 ASCII 标记」剔除，
纯数字（日期、证件号）与中文值不会被误伤。

**系统录入侧截图与客户材料一样要抽字段**：它是比对的**基准方**，取值抽不出来，逐字段比对就
退化成客户材料互相比对（单个来源会被判成「一致」）。`audit` 与平台物化步骤都会自动抽一遍，
需要单独补抽时用 `review.py extract-all --materials <包>`。

`extract-all` 的输出（平台会把它记进轨迹，模型不必解析）：

| 键 | 用途 |
|---|---|
| `requested` / `extracted` / `yield` | 本次请求的字段数、真正取到值的字段数、产率 |
| `system_side` | 按材料代号列出系统侧（基准方）的抽值情况 |
| `warnings` | 产率低于 50% 的材料（标签没对齐，或该栏确实多为空）—— 需要人工看一眼 |
| `by_material` | 每份材料的 `requested / extracted / missing_keys / written` |

## 三、findings.json 与核对表

`compare` 产出 findings.json，`report` 把它渲染成核对表 —— **默认同时产出 Markdown 与 HTML 两份**（`--html <路径>` 指定 HTML 位置，`--no-html` 才只出 Markdown）。两份来自同一份文档块（`report.py::build_blocks`），口径不会漂移。
findings.json 里除 `findings` 外还有几张给渲染器用的表，改动它们要同步 `scripts/report.py`：

| 键 | 用途 |
|---|---|
| `materials` | 材料清单（代号、类型名、来源文件、抽取字段数、side / required / compare_only） |
| `material_names` / `material_labels` / `material_types` | 材料**类型**→名称、材料**代号**→名称、代号→类型（宽表列头与排序用） |
| `missing_required` | 本轮缺失的必备材料 |
| `seal_summary` | 每份材料的盖章 / 签字三态 |
| `material_field_keys` | 每份材料已抽到的字段名（区分「材料没提供」与「材料里没这个栏目」） |
| `coverage.unchecked[].missing_materials` / `unmatched_materials` | 该未核字段的两种缺口（缺材料 / 字段名未对齐） |
| `coverage.by_missing_material` | 未核字段按缺口归并（核对表第一节） |
| `coverage.system_side` | 系统侧（基准方）取值覆盖：`types_present` / `empty_types` / `empty_type_names` / `fields_without_system_value` / `pass`。**系统侧整份材料一个字段都没抽出来时 `pass=false`，覆盖率闸门不通过** —— 那种情况下比对已经退化，结论不可采信 |
| `converged_out` | 按 P-04 收敛掉的多版本材料 |
| `extraction` / `system_side_coverage` / `stage_timing` | 仅 `audit` 返回：本次抽值明细（含产率告警）、系统侧覆盖、分段耗时 |

核对表章节：零 本轮材料完整性（**缺口置顶**）｜一 比对材料清单｜二 结论摘要｜
三 不一致/待确认汇总（A 严重风险 / B 不一致 / C 待确认 / D 印章签章）｜
四~八 逐份系统侧材料逐字段明细｜九 客户侧材料之间的专项比对｜十 材料清单及盖章情况｜
十一 核对结论｜十二 判定规则说明。

宽表的列由本轮**实际**提供取值的来源材料决定（系统侧在前、按材料类型排序），
列头与每行单元格由同一份列定义生成，不会错列；长取值截断到 120 字符，完整取值在
`findings[].sources` 里。

结论分五级：

| 级别 | 含义 | 计入一致率分母 |
|---|---|---|
| L1 | 严重风险（如疑似非本户材料，该材料不参与逐字段比对） | 否 |
| L2 | 不一致 | 是 |
| L3 | 待确认（单边为空、视觉三态、分类体系不同无法映射、含掩码姓名等） | 是 |
| L4 | 一致 | 是 |
| L5 | 系统独有（无外部来源可比） | 否 |

- 一致率 = 必核且判一致的字段数 / 必核字段数（必核且非 L5）。结论摘要里「一致（L4）」那一行
  是**全部字段**的 L4 计数（含非必核字段），通常大于一致率的分子 —— 两个数一起看，不是打架。
- 覆盖率 = 必核字段中有来源、被真正核到的比例。**未核字段必须在核对表里显式列出原因**，
  否则 `report` 拒绝出表（可用 `--force` 强行出表，未核章节会保留）。
- 覆盖率闸门还有一条**系统侧口径**：系统录入侧（基准方）某份材料一个字段都没抽出来时，
  闸门同样不通过 —— 此时逐字段比对已经退化成客户材料互相印证。摘要里会显式告警。
- 判定侧的「单边为空」是双向的：系统侧有值而客户侧全没读出 → L3；系统侧该栏为空而客户侧有值
  → L3。系统侧是基准方，不是对照方，**只有基准方有值时不算一致**。
- L2 必须给差异性质：错填 / 漏填 / 口径不同 / 材料本身有问题。
- 材料级问题（P-01 非本户、P-02 材料内部矛盾、P-03 必备材料或签章缺失、P-04 多版本、
  P-05 同人多角色）单独成章，不与字段级不一致混排。

`verify` 的命中口径有两种，都算命中，结果里用 `hit_scope` 区分：`line` 是引文落在某一行里，
`text` 是引文跨了相邻两行（版面换行把一个值切成两行，比如身份证住址）。只按单行比对会把
这种真命中误报成幻觉 —— 样例集上实测有 4 条。

**轨迹上报是自动的**：平台执行时会在环境里注入 `DWP_EXECUTION_EVENT_URL` / `DWP_AGENT_TOOL_TOKEN` /
`DWP_TRACE_ID`，每条子命令跑完都会自动上报一条轨迹（标题形如「比对 93 个字段」）。
你**不需要**手动调 `report_channel.py`；想补充说明时再调它即可。没注入地址时（本机自测）
自动跳过，行为完全不变。

`acceptance.py` 的覆盖率检查有两条判法：默认要求必核字段全核到；给了 `--baseline` 就按
「基线之外不得出现新增未核」判。样例材料集天然只覆盖整笔业务的一部分（13 份材料 vs 53 个
必核字段），基线把这件事写成显式数据（`tests/fixtures/sample-pack/coverage-baseline.json`），
**基线之外的新增未核仍然算失败**。想让比例门槛放宽就用 `--min-coverage <比例>`。

## 四、回话口径（面向业务同事）

1. 先给结论摘要：必核字段数、一致率、覆盖率、不一致与待确认各多少条、材料级问题几条。
2. 再列不一致明细，每条带四要素：字段名、来源材料类型、材料上的位置、归一化前后取值。
3. 单列「需人工补核 / 待确认」清单，写明为什么没结论。
4. 结尾固定一句：全部结论为机器提示，最终以人工审核为准；印章与签字类只出三态。
5. 不要复述脚本日志、不要把命令原文贴进答复。
