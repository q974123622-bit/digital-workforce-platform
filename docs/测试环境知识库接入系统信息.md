## 1. 总体调用链

```
身份(Identity) → 策略(Policy) → 网关(Gateway) → InternalKnowledgeAdapter → 内部知识引擎 → 审计(Audit)
```

- HTTP 入口：`POST /internal/knowledge/search`
- 请求体：`{"employee_id": "...", "knowledge_base_id": "...", "query": "...", "trace_id": "..."}`
- 业务代码禁止直接请求内部引擎，一律走 `app/services/gateway.py` 的 `search_knowledge()`。
- 关键实现文件：
    - `backend/app/services/gateway.py` — 策略判定 + 员工→知识库授权校验 + 审计
    - `backend/app/services/internal_knowledge_adapter.py` — 内部引擎适配器（只读检索）
    - `backend/app/services/knowledge_adapter.py` — 适配器基类与路由（仅 internal）
    - `backend/app/services/knowledge_registry.py` — 知识库登记/解析
    - `backend/app/routers/internal.py` — `/internal/knowledge/search` 路由

## 2. 知识库模式

知识检索统一走 `internal`（内部引擎，只读检索），已移除 mock/rag/volcengine_mcp 等演示模式。

当前本机 `.env` 已设置内部引擎配置。

## 3. 内部引擎接口（只读）

| 用途 | 方法 | 路径 |
| --- | --- | --- |
| 知识库列表（含描述） | GET | `/marketing_agent/api/v2/rag/kb/list` |
| 知识库详情 | GET | `/marketing_agent/api/v2/rag/kb/detail?kb_id=<ID>` |
| 分块检索 | POST | `/marketing_agent/api/v2/rag/chunk/retrieval` |

- 请求头：`Accept: application/json, text/plain, */*`、`x-org`、`x-tenant`、`X-User`、`Authorization`
- 列表参数：`page`、`page_size`（≤150）、`strict=true`、`filter_system_created=true`、`keywords`（按名称/描述模糊匹配）、`kb_id`（数组，只返回指定 ID）
- 列表响应结构：`data.items[]`，每项为 KnowledgeModel；其中 `description` 字段即为知识库描述，`doc_num` 为文档数，`name` 为库名。
- 详情响应结构：`data` 为 KnowledgeDetailModel（字段与 KnowledgeModel 一致，另有 `default_doc_state`、`warnings`、`rag_engine`）。
- 检索请求体（`enable_filters` 必须保持 `true`）：

```json
{
  "kb_id": 751,
  "question": "...",
  "similarity_threshold": 0.1,
  "dense_weight": 0.5,
  "top_k": 10,
  "top_n": 5,
  "enable_filters": true,
  "enable_rerank": true,
  "enable_llm_rerank": false
}
```

- 响应包络：`code == 0` 为成功，结果在 `data.chunks[]`，命中片段字段为 `docnm_kwd`（文档名）、`content_with_weight`（片段）、`rank_score` 或 `similarity`（打分）。
- 检索一次只查一个知识库；「AI员工 ↔ 多个知识库」的多对多授权尚未实现。
- 完整接口文档（创建/更新/删除、文件夹、文档、chunk、检索等 22 个接口）参考公司内部《知识引擎接口文档md.md》。

## 5. 知识库授权分配方案（目标状态：分身无权限，AI员工无交叉分管）

原则：

- 两个数字分身（正式员工分身、实习生分身）**不持有任何知识库访问权限**；遇到不会的知识问题只能求助（fallback 到 AI员工平台）。
- 当前知识库由两个岗位 AI员工分管，分配结果**完全无交叉**。
- L3 客户敏感库不参与默认分配，保持白名单审批专用。

| 主体 | 角色 | 知识库授权 | 插件等级 | 说明 |
| --- | --- | --- | --- | --- |
| DT-E10281 | 正式员工数字分身 | 无 | 无 | 不直接访问任何知识库；遇到知识问题求助 AI-GENERAL |
| DT-E20999 | 实习生数字分身 | 无 | 无 | 不直接访问任何知识库；遇到知识问题求助 AI-GENERAL |
| AI-GENERAL | AI员工平台（综合服务） | KB-PUBLIC、KB-ONBOARD、KB-INTERNAL、KB-IT-SERVICE、KB-REG-INTERNAL、KB-REG-EXTERNAL | knowledge-l1 + knowledge-l2 | 通用/入职、内部制度、外部监管、IT 服务 |
| AI-INVESTMENT | 投资分析 AI员工 | KB-SECURITIES、KB-INVESTMENT-BANKING | knowledge-l2 | 证券业务、投行咨询 |
| — | KB-CUSTOMER-SENSITIVE（L3） | 不分配 | 白名单审批 | 客户敏感信息库，不默认授予任何 AI员工 |

- AI-GENERAL（6 库）与 AI-INVESTMENT（2 库）的知识库授权完全无交集。
- 求助链路：两个分身的 `fallback_employee_id` 均指向 `AI-GENERAL`；分身自身不发知识库检索，遇到问题由 AI员工平台代为查询并回答案源。
- 插件等级必须覆盖库等级：AI-GENERAL 分管 L1/L2 库，故需 `knowledge-l1` + `knowledge-l2`；AI-INVESTMENT 只分管 L2 库，仅需 `knowledge-l2`。
- 授权判定顺序：先按数据等级走插件策略（knowledge-l1/l2/l3），再按 `AgentKnowledgeGrant` 表做员工→具体库校验；未获授权返回 403 并写审计（`policy_id=AGENT-KB-GRANT`）。

## 7. 获取知识库描述的步骤

引擎已在「知识库列表」接口的每个 item 中直接返回 `description` 字段（另可用详情接口按 ID 单查），无需逐个调用详情接口。

### 方式一：列表接口一次拿到全部（推荐）

1. 准备好 `tools/.env` 中的引擎凭据（地址、x-org、x-tenant、X-User、Authorization）。
2. 请求列表接口（GET）：

```
/marketing_agent/api/v2/rag/kb/list?page=1&page_size=150&strict=true&filter_system_created=true
```

1. 判断分页：响应 `data.items` 数量达到 `page_size`（150）时，继续请求 `page=2、3…`，直到不足一页为止（本次探测共 3 页、318 个库）。
2. 从每个 item 提取 `id`、`name`、`description`、`doc_num` 即可得到「名称 → 内部 ID → 描述」清单。
3. 对指定库快速过滤：列表接口传 `kb_id=[751,756]`（数组）或 `keywords=证券`（按名称/描述模糊匹配）。

### 方式二：详情接口按 ID 单查

```
GET /marketing_agent/api/v2/rag/kb/detail?kb_id=751
```

- 响应 `data` 含 `description`（其余字段与列表项一致）。
- 适用场景：只关心少数几个库、需要 `default_doc_state`/`warnings`/`rag_engine` 等扩展字段时。

### 已有脚本

- `tools/list_internal_kb.py`：列表翻页 + 输出 ID/名称/文档数（可自行加打印 `description`）。
- 本次探测是临时脚本按上述方式一完成；结束后临时脚本已删除，未落地结果文件。
- 安全注意：仅使用只读 GET；凭据从 `tools/.env` 读取且不回显；结果描述属业务信息，可入文档，但凭据与内部地址不可入文档。

- 越权拒绝（已实测）：`AI-INVESTMENT + KB-IT-SERVICE` → `403`，审计 `deny`（AGENT-KB-GRANT）。
- 审计查询：`GET /api/v1/audit`。
