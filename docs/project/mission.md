# AI员工平台使命

> 状态：草案
> 适用对象：项目成员、产品与工程负责人、Codex、Copilot 等 AI 开发工具
> 项目前身：数字员工平台 Demo

## 1. 我们想建设什么

我们设想的不是给每个业务系统再增加一个聊天框，也不只是把若干 Agent 放进同一个管理后台，而是让 AI 以新的工作主体进入企业。

正式员工可以拥有代表自己的数字分身；公司可以创建有工号、有岗位、有负责人、有独立记忆和能力边界的虚拟员工；已有 Agent、RPA 和工作流也可以作为员工或员工能力接入。它们能够在企业微信、e家等员工熟悉的入口中被找到，也能够像真实项目成员一样协作完成任务。

AI员工平台承载这种新的工作关系。它连接真人员工、数字分身、AI员工、组织流程和企业资源，使 AI 不仅能够回答问题，还能够在授权范围内受理工作、参与协作、推进流程、反馈结果，并留下完整记录。

我们的长期使命是：

> 将公司真实的人员、岗位、权限、流程和协作方式映射到数字工作体系，让真人与 AI员工按照企业实际的办公逻辑共同工作。

## 2. 项目从哪里来

项目最初通过数字员工平台 Demo 验证了三种构想：真人员工可以拥有数字分身，公司可以创建新的虚拟员工，多个数字员工可以通过 Agent Team 协作。同时，知识库、MCP、Workflow、RPA 和其他 Agent 能够在统一权限与审计边界内被调用。

Demo 之后，我们看到的真实问题不只是“怎样做一个效果更好的问答机器人”，而是：当越来越多部门开始拥有自己的 Agent 时，这些 Agent 怎样进入公司的组织和工作体系。

投研部门已有 Agent 是目前观察到的重要需求信号和潜在接入对象。相关部门已经了解过现有 Demo，但尚未形成正式接入需求、范围和排期。因此，它说明平台存在现实接入价值，但当前不构成已经承诺的交付任务。

平台既要支持我们创建新的 AI员工，也要允许公司已有 Agent 以可识别、可配置、可治理的方式“上岗”，避免它们继续以相互孤立的工具形态存在。

## 3. 最终产品逻辑：映射真实办公闭环

平台应尽量遵循公司员工已经熟悉的办公逻辑，而不是为 AI 重新发明一套脱离组织现实的流程。

一个典型工作闭环包括：

```text
真人员工提出需求并授权
        |
        v
数字分身代表本人发起或跟进事项
        |
        v
现有企业流程完成申请、审批与流转
        |
        v
负责该岗位的AI员工受理并实施
        |
        +--> 涉及多个岗位时，建立群聊或协作任务
        |
        v
数字分身接收进度与结果并反馈真人
        |
        v
真人确认或验收，任务结束并完整留痕
```

例如，一名新员工申请电脑时，现实中需要填写申请、逐级审批、由 IT 服务人员联系和实施，最后由申请人验收。映射到平台后，可以由新员工的数字分身代表本人发起和跟进申请；审批完成后，数字分身与 IT服务员工对接；如果涉及采购、资产或权限等多个岗位，可以建立群聊，由相关真人或 AI员工共同参与；实施结果由数字分身反馈给真人，真人完成最终验收，后台保存整个过程。

当前 MVP 不要求完整实现这一示例。它是长期产品设计的方向标，用来检验每个阶段建设的能力是否最终能够回到真实办公闭环。

## 4. 平台中的工作主体

### 4.1 真人员工与数字分身

数字分身在业务语义上代表真人员工，不是一个与真人无关的新角色。它应理解并使用真人被授权的工作信息、组织关系和常规权限，帮助真人接收消息、发起事项、协调工作和汇总结果。

数字分身仍应使用独立的技术身份执行和留痕，以便区分真人操作与分身代办。涉及敏感数据、高风险权限或关键业务操作时，最终确认和责任必须回到真人；数字分身不能以“代表真人”为由绕过审批、审计和安全控制。

### 4.2 虚拟员工

虚拟员工代表公司新增的数字化岗位，例如 IT服务员工、投研投顾助手、分析师助手、新员工入职助手、维护人员或带教导师。它拥有独立工号、岗位职责、真人负责人、知识范围、Skill、工具权限、记忆和运行环境。

虚拟员工应像一个被管理的岗位一样工作：知道自己负责什么、不负责什么，能够受理事项、反馈状态，必要时请求审批或转交其他岗位。

### 4.3 已有 Agent、RPA 与其他能力

已有业务 Agent、RPA、OpenClaw、Workflow 或其他自动化能力，可以根据职责被纳管为独立员工，也可以作为某个 AI员工被授权使用的能力。平台不要求所有能力采用同一种实现，但要求它们进入统一的身份、权限、调用和记录边界。

### 4.4 Agent Team

Agent Team 不是另一类员工，而是跨岗位任务的协作方式。简单事项可以通过私聊由一个 AI员工完成；复杂事项可以建立群聊或协作任务，由数字分身、多个 AI员工、RPA 以及必要的真人共同参与，完成拆解、分工、审批、实施和汇总。

## 5. 平台总体框架

AI员工平台由员工可感知的工作入口、企业控制面、AI员工运行面和受控企业资源共同组成。

```text
企微 / e家 / Web-H5 / 内部API
              |
              v
统一交互、身份映射与AI员工路由
              |
              v
组织、账号、负责人、AI员工注册与生命周期
              |
              v
独立上下文、记忆、Skill与Runtime
              |
              v
Policy / 知识库 / MCP / Workflow / RPA
              |
              v
任务状态、引用、轨迹、审批与审计
```

员工的主要使用入口应尽量融入已有聊天工具，并通过卡片式 H5 展示任务、审批和结果，而不是要求所有员工学习一个充满技术概念的独立 AI 后台。管理后台仍然重要，但主要服务于 AI员工配置、组织和权限管理、运行观察、安全与运维。

安全、审计、部署、运维、备份和历史数据处理不是产品使命本身，却是 AI员工进入真实企业工作的必要条件。平台必须从 MVP 阶段开始保留这些边界，并随使用范围逐步加强。

## 6. DSH 与 AI员工运行体系

当前阶段，DSH 是 AI员工运行面的核心底座之一。我们优先围绕 DSH 验证每个 AI员工相对独立的上下文、记忆、Skill、工具调用和执行环境，并将权限和企业资源调用纳入平台控制。

长期来看，AI员工平台不应永久锁死在单一 Runtime 上。平台需要逐步沉淀统一的 Harness 契约和生命周期管理，使 DSH 成为核心但可插拔的 Runtime 实现，同时允许其他适合公司场景的运行时接入。

Runtime 可以扩展，AI员工的身份、负责人、权限、资源边界和工作记录必须保持统一。

## 7. 当前 MVP

当前目标不是一次性实现完整办公闭环，而是在公司内部测试服务器上跑通第一个真实、受控、可重复的 AI员工使用链路。

企业微信机器人连接和内部知识库连接已经分别完成测试。下一阶段将它们与现有平台正式串联：由项目组成员通过一个企业微信测试机器人访问一个 IT服务员工，使其在授权范围内使用内部 IT 服务知识库和内部模型完成问答，并记录必要的会话、调用结果和失败状态。

这个 MVP 验证的不是“IT问答就是平台的最终产品”，而是验证入口、身份、AI员工、Runtime、知识资源和后台记录能否在内部环境中形成最小闭环。详细范围、验收条件和上线步骤应进入 `roadmap.md` 或具体 OpenSpec，而不是继续扩充在 Mission 中。

## 8. 长期目标

当第一个闭环稳定后，平台将根据真实需求逐步扩展，而不是一次性铺开所有能力：

- 从 IT服务员工扩展到投研投顾助手、分析师分身、数据研发、数据取数和内部日常事务；
- 支持已有部门 Agent 接入，并逐步建立 AI员工的上岗、调整、评估和退出机制；
- 从单员工私聊扩展到数字分身牵头的多岗位群聊和 Agent Team 协作；
- 接入知识中心、AI知识库、e家、CRM 等内部 MCP 或受控接口；
- 发展 AI员工的长期记忆、Skill、工具使用和任务执行能力；
- 打通 Workbuddy 等 Skill 体系，形成可复用的公司能力资产；
- 逐步形成能够完成内部日常事务和开发流程的 multi-agent Harness。

长期目标不是追求不受约束的自动化，而是让 AI员工在组织关系、岗位责任和人类授权之内承担越来越完整的工作。

## 9. 滚动建设与自举

项目采用 MVP 方式滚动建设。每个阶段优先选择真实但风险可控的场景，跑通一个可观察的闭环，再根据使用反馈决定继续、调整或重构。MVP 失败并不可怕，只要失败能够被真实识别、经验能够被保留，并能快速形成更合适的下一版本。

平台也应尽早服务自身建设过程。AI 可以参与 Coding、数据研发、数据取数、AI网关迭代、记忆与 Skill 建设以及 AI员工本身的迭代；团队通过 SDD、模块边界、测试和审计控制 AI 开发过程，逐步形成“用 AI 建设和改进 AI员工平台”的自举能力。

这种自举不是让 AI 脱离人类决策自行改变平台。产品方向、敏感权限、正式上线和关键架构仍由人类负责；AI承担被授权的设计、实现、验证和重复性工作。

## 10. 与其他项目文档的关系

- `CONSTITUTION.md` 规定项目长期不可违反的工程与治理底线；
- 本文保存产品构想、长期使命、总体框架和当前验证方向；
- `tech-stack.md` 记录技术现状、选型、演进状态和环境约束；
- `roadmap.md` 记录阶段目标、需求优先级和验收节点；
- 架构文档描述平台模块、数据流和系统边界；
- OpenSpec 记录具体需求、设计、任务和验证方式。

Mission 可以根据新的真实需求由人类评审修订，但不能因为某个 Demo、临时技术选型或局部实现方便，就无意中改变项目最终要解决的问题。
