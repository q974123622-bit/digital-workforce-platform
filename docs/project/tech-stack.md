# AI员工平台技术基线

> 状态：草案
> 适用对象：项目成员、技术负责人、Codex、Copilot 及其他参与开发的 AI 代理
> 上游依据：`CONSTITUTION.md`、`mission.md`
> 基线范围：当前仓库已合并内容；未合并的个人分支和构想不作为当前事实

## 1. 文档目的

本文记录 AI员工平台当前采用的技术、已验证能力、默认建设路线和环境约束。它不是永久不变的技术白名单，也不要求所有 AI员工采用同一种内部实现。

项目采用“硬性边界、默认路线、实验通道”三层技术治理方式：

```text
硬性边界：所有正式能力必须遵守的安全、契约与治理要求
    |
    v
默认路线：大多数需求优先复用的成熟实现
    |
    v
实验通道：允许隔离验证的新框架、新模型和新 Runtime
```

我们统一的是平台边界、数据契约和进入企业工作的条件，而不是把每个 Agent 的实现永久写死。技术选择可以演进，但不能以探索为由绕过身份、权限、审计和部署约束。

## 2. 技术状态定义

本文使用以下状态，避免把 Demo、目标架构或尚未合并的代码描述为正式能力：

| 状态 | 含义 |
| --- | --- |
| `CURRENT` | 当前仓库中已经存在的实现，不代表已经适合正式使用 |
| `VERIFIED` | 已通过独立连接或链路测试，仍可能尚未收编进统一平台 |
| `DEFAULT` | 新增常规需求应优先采用的默认路线，偏离时需要说明理由和影响 |
| `EXPERIMENTAL` | 隔离验证中的能力，不得默认进入正式链路 |
| `TARGET` | 已明确的演进方向，但尚未完成 |
| `TBD` | 需要结合真实环境、接口或需求进一步确认 |

当实现状态变化时，应基于可验证证据更新本文。未经合并、部署或测试的能力不得自行提升状态。

## 3. 长期硬性边界

- 业务逻辑不得直接绑定企业微信、模型厂商、知识引擎、数据库或 Agent 框架的专有 SDK；外部能力必须通过平台 Adapter、Provider 或 Gateway 边界接入。
- 身份解析、权限决策、AI员工路由、资源调用和审计记录不得由渠道层或单个 Agent 私自实现一套旁路。
- 配置和凭据必须与代码分离，通过环境变量或公司批准的安全配置机制注入；真实密钥、Token 和内部数据不得进入 Git、Prompt、普通日志或截图。
- 外部调用必须具有明确的超时、错误映射和可观察状态。真实依赖不可用时应显式失败，禁止静默切换到 Mock 或虚构结果。
- 正式能力必须能够识别调用主体、目标 AI员工、使用的资源和执行结果，并为后续审计保留必要记录。
- 影响公共 API、数据结构、权限、外部系统、跨模块边界或部署方式的技术变化，应先通过对应 OpenSpec 明确契约和验收方式。

## 4. 当前默认技术路线

### 4.1 Web 与 H5

| 技术 | 状态 | 定位 |
| --- | --- | --- |
| React 18、TypeScript、Vite | `CURRENT` / `DEFAULT` | 当前 Web 前端及近期新增页面的基础技术 |
| Ant Design | `CURRENT` | 维护现有管理页面，避免为统一外观一次性重写 Demo |
| Tailwind CSS 与成熟 UI 库 | `TARGET` | 新增聊天入口和卡片式 H5 的优先路线，具体组件库在对应需求中确定 |

前端采用渐进共存策略。现有 Ant Design 页面可以继续维护；新增员工交互页面优先采用 Tailwind CSS 和成熟组件能力，旧页面仅在真实需求触及时逐步迁移。不得同时建设两套重复的业务逻辑或数据访问层。

### 4.2 平台后端与数据

| 技术 | 状态 | 定位 |
| --- | --- | --- |
| Python、FastAPI、Pydantic | `CURRENT` / `DEFAULT` | 平台 API、契约校验和核心业务服务 |
| SQLAlchemy | `CURRENT` / `DEFAULT` | 数据访问边界，降低业务逻辑对具体数据库的绑定 |
| SQLite | `CURRENT` / `DEFAULT` | 本地开发及当前单机 MVP 的默认数据库 |
| PostgreSQL | `TARGET` | 扩大试点、增加并发或提高恢复要求前的目标数据库 |

当前服务器 MVP 可以继续使用 SQLite，但不得把 SQLite 特性扩散到业务层。是否迁移 PostgreSQL，应在扩大用户范围前结合并发、备份恢复和运维条件评审，并通过独立变更实施。

### 4.3 渠道与企业微信

| 技术 | 状态 | 定位 |
| --- | --- | --- |
| Node.js 企业微信 Gateway | `CURRENT` / `VERIFIED` | 使用企业微信智能机器人长连接接收消息并调用平台后端 |
| 其他渠道 Adapter | `TARGET` | 后续接入 Web/H5、e家或内部 API 时复用统一消息与身份边界 |

渠道层只负责连接、消息格式转换、必要验证、身份线索传递和回复发送。AI员工选择、知识检索、权限判断和业务规则应留在平台侧。

### 4.4 AI员工 Runtime、模型与知识

| 能力 | 状态 | 定位 |
| --- | --- | --- |
| DSH | `CURRENT` / `DEFAULT` | 当前阶段 AI员工运行面的核心底座之一 |
| 可插拔 Harness / Runtime | `TARGET` | 允许既有 Agent 或其他 Runtime 按统一生命周期和治理边界接入 |
| DeepSeek 公网兼容接口 | `CURRENT` | 开发期已有模型实现，不是测试环境的强制依赖 |
| DashScope Embedding | `CURRENT` | 开发期已有嵌入实现，不是测试环境的强制依赖 |
| 内部模型或 AI 网关 | `TARGET` / `TBD` | 测试环境优先接入，具体协议、模型和地址待内网确认 |
| 内部知识库 | `VERIFIED` | 已独立完成连接测试，尚待通过正式 Knowledge Adapter 收编到平台链路 |

DSH 可以继续演进，但不得成为业务模型中的唯一可能实现。长期应沉淀 Runtime/Harness 契约，使 DSH 保持核心但可替换；新 Runtime 接入后仍需接受平台统一身份、权限、资源和审计控制。

## 5. 可替换能力边界

以下边界用于保持平台统一，同时为不同 Agent 和企业资源保留实现空间：

- **Channel Adapter**：连接企微、Web/H5、e家和内部 API，并转换为统一交互语义。
- **Identity / Directory Provider**：将外部用户身份映射为平台员工、组织和授权主体。
- **Agent Registry / Router**：描述 AI员工身份、岗位、负责人和运行目标，并完成受控路由。
- **Runtime / Harness Provider**：管理 Agent 的启动、上下文、执行、停止和结果返回。
- **Model Provider**：隔离模型协议、网关地址、模型名称和供应商差异。
- **Knowledge Adapter**：隔离知识库、检索应用、知识域和底层检索接口差异。
- **Tool / MCP / Workflow / RPA Adapter**：将企业能力作为受控工具提供给 AI员工。
- **Storage Provider**：隔离业务数据、会话、记忆和审计存储的具体实现。
- **Audit / Telemetry Provider**：统一记录轨迹、引用、错误和必要运行指标。

本文只定义这些能力边界，不提前规定具体 API 字段、类名或数据表。详细契约应在真实接入需求出现时，通过架构设计或 OpenSpec 决定。

## 6. 默认路线与实验通道

常规功能应优先沿用 `DEFAULT` 技术，以降低部署、测试和维护成本。采用不同框架、模型、知识方案或 Runtime 时，实验者应说明实验目标、负责人、隔离方式和退出条件。

实验能力可以放在独立模块、分支、沙箱或受控测试环境中，但必须满足以下要求：

- 不接触未经授权的真实数据和生产凭据；
- 不绕过平台身份、权限、Gateway 和审计边界；
- 不改变默认链路或让其他模块被迫依赖实验组件；
- 能够被关闭或移除，不影响当前 MVP；
- 明确标记为 `EXPERIMENTAL`，不得对外宣称已经正式可用。

实验只有在证明能够解决真实需求、通过相关兼容性与失败场景测试，并经人类评审后，才可升级为 `DEFAULT`。涉及公共契约、数据、权限、部署或跨模块变更时，还必须先完成对应 OpenSpec。

## 7. 开发环境与分工

三个环境的网络能力和操作方式不同，不要求它们访问完全相同的服务：

| 环境 | 可用能力 | 主要用途 | 约束 |
| --- | --- | --- | --- |
| 外部本机 | 可访问 Codex 及必要公网开发资源，无法访问公司内网 | 文档、设计、非敏感代码开发和离线测试 | 禁止保存或上传公司真实内部数据，不得形成部署所需的公网运行依赖 |
| 公司 Windows 主机 | 可访问公司内网及部分境内网站，可使用 VS Code、Copilot | 内网接口联调、受控开发、部署包准备和效果验证 | 只能使用公司允许的工具和数据处理方式 |
| Linux 测试服务器 | 主要访问公司内网，经堡垒机操作，可通过受控方式上传文件 | MVP 部署、集成验证和最终验收 | 无法直接 SSH，公网和软件安装受公司网关及服务器条件限制 |

代码应保存在同一 Git 仓库并通过提交传递，不依赖截图或手工复制来维持长期同步。具体在哪个环境修改，由数据敏感性、接口可达性和工具便利性共同决定；涉及真实内网数据和接口的验证必须回到受控环境完成。

## 8. 网络、构建与部署基线

- 测试环境优先使用公司内部模型、知识库及 AI 网关；平台本身不额外封锁网络，实际可达范围由公司网络策略决定。
- 企业微信等必要外部渠道应在部署前检查连通性；若被公司网关拦截，应申请明确的域名和端口白名单，而不是在程序中绕过限制。
- 公网 DeepSeek、DashScope 等可以用于不含内部数据的开发验证，但不得被写成测试环境必须可访问的服务。
- 模型、知识库和工具端点必须可配置，业务代码不得写死供应商域名、模型名或凭据。
- 构建与运行应分离。依赖包、前端静态资源和容器镜像可以在合适环境准备并通过批准方式传入测试服务器，运行时不得再隐式下载依赖。
- 前端和后端运行时不得隐含依赖公共 CDN、在线字体、境外遥测、在线许可证检查、自动更新或临时安装脚本。
- 后续应结合测试服务器实际软件、内部镜像源和运维要求，确定容器、进程托管、反向代理、日志、备份和恢复方案；在核实前统一标记为 `TBD`。

部署前至少验证企业微信连接、平台健康状态、内部模型或网关、指定内部知识库以及持久化目录。依赖不可达时必须返回真实错误并留下可诊断记录，不得使用 Mock 冒充测试环境闭环成功。

## 9. 维护规则

- 本文记录技术事实、默认选择和演进方向，不记录密钥、端口、接口字段、安装命令或短期 Sprint 任务。
- 技术版本升级、数据库迁移、Adapter 契约和部署方案应由对应 OpenSpec 或专项设计承载。
- 新技术不是因为“更先进”就自动成为默认路线；现有技术也不是因为已使用就永久不可替换。
- 当默认技术无法满足真实需求时，应优先形成可验证实验，再根据维护成本、环境适配、安全和实际效果决定是否晋升。
- `roadmap.md` 负责把测试服务器上线、内部模型和知识库闭环拆成阶段目标，本文不替代路线图。
