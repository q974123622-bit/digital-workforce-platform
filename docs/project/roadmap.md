# AI员工平台路线图

> 状态：草案
> 适用对象：项目成员、Feature负责人、Codex、Copilot 及其他参与开发的 AI 代理
> 上游依据：`CONSTITUTION.md`、`mission.md`、`tech-stack.md`
> 当前主线：内部测试服务器上的 IT服务员工 MVP

## 1. 路线图的使用方式

本文用 Feature Unit 组织近期工作。一个 Feature Unit 是可以交给一个 Agent 独立负责、具有明确输入输出和验收边界的工作单元，不等同于函数级任务，也不自动对应一份 OpenSpec change。当前只对测试服务器 MVP进行原子化拆分；后续方向等真实需求出现后再展开。

每个 Feature 只设置一名主责 Owner。Owner 可以请求其他成员提供接口、环境或评审支持，但不得顺手修改其他 Feature 的职责范围。公共接口发生变化时，必须先通知所有依赖方并更新对应设计或 OpenSpec。

Feature 使用以下状态：

| 状态 | 含义 |
| --- | --- |
| `READY` | 输入与边界已经足够清楚，可以分配并开始 |
| `BLOCKED` | 存在尚未满足的前置依赖 |
| `IN_PROGRESS` | 已有唯一主责 Owner 正在推进 |
| `VERIFIED` | 技术验收通过，尚待里程碑整体确认 |
| `ACCEPTED` | 已纳入里程碑并由人类确认完成 |
| `DEFERRED` | 暂不推进，等待新的真实需求或外部条件 |

状态只能依据证据更新。本地运行成功、独立接口连通和测试服务器上线是三个不同层级，不得互相替代。

## 3. 测试服务器 MVP完成定义

只有以下条件同时满足，阶段一才能标记为完成：

- 项目组成员可以访问现有 Web前端，并能通过企业微信测试机器人与同一个 IT服务员工交互；
- IT服务员工在 Linux 测试服务器上由真实 DSH Runtime运行，不能以 `Demo Adapter降级` 代替成功；
- DSH和平台通过公司可用的内部模型服务完成真实推理，不依赖公网模型作为隐式兜底；
- IT服务员工只访问指定内部 IT知识域；知识接口返回来源信息时应在平台链路中保留，但前端引用展示不作为当前 MVP硬性门禁；
- 无检索结果、无权限、模型不可用、知识库不可用和渠道异常均明确反馈，禁止静默返回 Mock或虚构答案；
- Web与企微请求均能关联用户、AI员工、会话、DSH执行、模型调用、知识调用和最终结果；
- 服务能够按固定发布物启动、停止和重启，日志可定位问题，历史数据能够备份并完成一次恢复验证；
- 既有自动化测试和保留的 Demo主链未被新增真实链路破坏；
- 最终结果由一名人类项目成员复核并明确确认。

## 5. 后续演进方向

以下方向暂不拆成原子 Feature。只有出现正式需求、负责人、允许使用的数据和明确验收场景后，才进入近期路线图。

### 5.1 既有 Agent上岗试点

投研部门已有 Agent完成正式需求确认后，可以作为首个外部 Agent接入对象。进入条件包括明确的业务负责人、职责范围、数据权限、现有接口、部署环境和试点用户；当前意向不构成交付承诺。

### 5.2 多 AI员工与生命周期

从单 IT员工扩展到多个岗位，逐步完善注册、负责人、版本、运行状态、调岗、停用和退出机制。进入条件是至少出现第二个真实岗位需求，而不是为了展示数量提前创建员工。

### 5.3 数字分身、流程与团队协作

围绕真实办公事项引入数字分身、审批、群聊、Agent Team和真人验收。优先选择一个能够完整描述发起、流转、执行、反馈和验收的低敏感场景，不直接把旧 Demo协作流程视为正式实现。

### 5.4 更多入口与企业资源

按真实需求接入 e家、卡片式 H5、CRM、知识中心及其他内部 MCP。每个入口和资源继续遵守统一 Identity、Policy、Gateway、Adapter和 Audit边界。

### 5.5 内部 multi-agent Harness

在多个真实 AI员工和 Runtime接入后，沉淀可插拔 Harness契约、上下文与记忆边界、Skill体系、任务生命周期和跨员工协作机制。DSH保持核心实现之一，但平台不永久绑定单一 Runtime。

### 5.6 统一模型与 AI 网关

当平台出现多个模型来源、多个 AI员工的统一路由、配额、成本、可用性或合规治理需求后，再评估建设或接入统一模型与 AI 网关。当前 MVP只连接公司已经提供的内部模型服务，不提前建设平台级网关。

### 5.7 知识体验与内容治理

当前优先复用公司内部火山知识库已有的检索和问答能力，不提前建设独立 RAG优化体系。只有真实试用反馈证明存在稳定问题后，才区分问题来自平台接线与知识域选择、火山侧可配置能力、知识底料质量还是前端呈现，并据此决定是否建设评测集、调整可控参数、治理知识内容或增加引用展示。

## 6. Agent协作与OpenSpec规则

- 每个 Feature只有一名主责 Owner；开始时由人类或集成人指定，未指定时保持 `TBD`。
- Agent只接收所属 Feature所需的代码、文档和接口上下文，不需要读取全部历史 Sprint记录。
- Owner必须遵守“允许修改范围”和“不修改范围”；发现必须跨界时暂停该部分并通知依赖 Owner或集成人。
- 共享契约先于并行实现冻结；接口变更由契约 Owner统一处理，调用方不得各自创建兼容版本。
- Feature达到自身验收条件只能标记为 `VERIFIED`；只有被后续里程碑接纳后才能标记为 `ACCEPTED`。
- 纯环境核查、事实盘点和不改变外部行为的部署准备不强制创建 OpenSpec change。
- 涉及公共 API、数据、权限、外部系统、跨模块行为或部署模型的 Feature，必须按照项目宪法在实施前进入 OpenSpec。
- 本路线图确认后，首个 OpenSpec change应以“测试服务器 IT服务员工 MVP”为统一目标，实施任务按 F00至 F09分组；Feature Owner不分别生成重复的总体规范。
- OpenSpec只保存具体需求、设计、任务和验收，不复制本文的长期路线和未来构想。

## 7. 路线图维护

- 近期 Feature可以随真实环境事实调整状态、依赖和验收条件，但不得无证据宣称完成。
- 新需求先判断属于现有 Feature、后续方向还是新的里程碑，禁止直接插入正在验收的 Feature扩大范围。
- 当某项技术选择阻碍真实 Agent接入时，应先回到 `tech-stack.md`评估默认路线或实验通道，而不是在单个 Feature中偷偷建立新标准。
- 当产品使命、当前技术或项目底线发生变化时，应先更新对应上游文档，再同步本路线图。
- 本文不记录具体日期、端口、凭据、函数级任务或未经环境验证的工期承诺。
