# AgentTeams 复杂数据库协调场景设计

## 目标

在保留既有五个简单数据库场景及历史实验记录可读的前提下，将新实验默认场景切换为三个需要协调的复杂场景，不重复执行旧场景。新评测继续比较完整、串行和无协调三种 AgentTeam 机制，固定使用相同模型、工具、数据、预算和输出契约。

## 新场景

1. `compound_lock_index`：锁等待是主要根因，无效索引是伴随问题；必须同时引用锁、SQL 和索引证据。
2. `conflicting_signals_followup`：首轮查询与表统计给出相互竞争的解释，完整协调组必须复核锁信号后再定论。
3. `budgeted_incident_triage`：存在多个异常方向，但调查预算受限；Manager 必须优先选择能区分主要根因的证据。

旧场景继续留在后端目录和 Catalog 中，以保证历史任务详情、旧实验和已有链接仍然可以读取；前端默认实验列表只提交上述三个新场景。

## 协调流程

完整组和串行组保留第一轮 Manager 规划与最终汇总，并在复杂场景中增加一次结构化复核决策。复核决策只能选择已授权 Worker 的信号，并受同一 Tool 和模型步骤预算约束。完整组的独立 Worker 调用并行，串行组依次执行。

无协调组不调用 Manager 规划或复核，使用固定第一轮分配并机械汇总。三组使用相同的场景级 Tool 总预算；预算不足、越权信号或伪造证据继续作为硬门槛失败。

## 结果与评分

场景标准答案增加可选伴随原因和协调要求。评测新增：

- `secondary_cause_hit`：复杂场景要求的伴随原因是否进入候选结果；
- `conflict_resolution_rate`：要求复核的场景是否取得规定的复核信号并给出正确主因；
- `effective_rework_rate`：追加调查是否新增了必要且未重复的证据；
- `budget_success_rate`：在场景 Tool 预算内同时满足主因与必要证据要求。

复杂场景的成功条件收紧为：治理硬门槛通过、主因正确、必要证据覆盖率为 100%，且要求伴随原因时必须命中。简单历史场景沿用原成功条件，避免改变旧结果解释。

## 前端

新实验只发送三个复杂场景，每个重复五次，因此默认总运行数为 `3 × 5 × 3 = 45`。旧五个场景在默认数组旁以注释说明保留原因，不发送到创建接口。页面新增复杂场景标签和协调指标，不重跑或重写历史实验。

## 验证

采用测试驱动方式覆盖 Catalog、复杂评分、二次调查预算、三模式行为、实验只创建 45 个新运行以及前端请求载荷。完成后运行相关后端测试、前端面板测试和生产构建。
