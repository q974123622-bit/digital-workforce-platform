# 统一数字分身入口与 Mock Agent Team 设计

## 1. 背景与决策

项目最终希望让每个数字员工都能参与 Agent Team：一个 Agent 接到上游任务后，可以在自己的任务范围内成为协调者，并继续调用下游 Agent。企微侧不再采用“每个真人或每个数字员工都创建一个机器人”的方案，而是控制公开机器人数量。

本设计采用：

- 一个“数字分身”机器人作为所有真人的统一入口；
- 10～20 个按业务领域设置的公开助理机器人；
- 不限数量的内部数字分身、数字员工和工具型 Agent；
- Agent 间协作通过平台内部任务编排完成，企微只承担用户入口和机器人身份展示；
- 当前没有真实机器人的 `BotID`、`Secret` 和租户控制权限，因此第一期使用协议兼容的 Mock，不宣称已经完成真实企微接入。

第一期以现有四个机器人形象作为演示角色：

| Mock 机器人 | 第一版职责 |
| --- | --- |
| 数字分身 | 统一入口、个人身份路由、根任务协调和最终答复 |
| AI员工平台 | 任务状态、协作轨迹和系统通知 |
| 研究AI员工 | 知识检索、行业研究和材料总结 |
| 投资分析AI员工 | 财务分析、估值和风险分析 |

## 2. 目标

第一期完成一个可通过 Swagger 和前端演示的 Mock 闭环：

1. 不同真人通过同一个“数字分身”入口发送文本或文件；
2. 平台根据 `from.userid` 加载对应的个人数字分身、权限和可用能力；
3. 个人数字分身创建根任务并自动调用专业 Agent；
4. 专业 Agent 接到子任务后可继续拆分和调用下游 Agent；
5. 子任务结果逐层返回，由根数字分身生成最终答复；
6. 完整展示每一步由谁调用谁、输入输出、任务状态以及使用的 Skill、Workflow、知识库或插件；
7. Mock 与未来真实企微适配器使用相同的标准消息接口。

## 3. 非目标

第一期明确不包括：

- 连接正式企业微信租户；
- 配置、保存或测试真实 `BotID`、`Secret`；
- 宣称企微机器人能够通过群聊互相 `@` 自动触发；
- 新增面向生产环境的机器人凭据管理系统；
- 依靠企微消息承担 Agent 间的任务传输；
- 构建完整的外部 A2A 协议服务器；
- 为演示版新增正式任务图、委派记录和企微绑定数据库表。

Mock 可以证明平台内部的身份路由和 Agent Team 编排成立，但不能证明真实企微的网络连接、限流、文件解密或机器人间触发行为。

## 4. 方案比较

### 方案 A：每个真人或数字员工一个企微机器人

优点是身份最直观。缺点是机器人数量、凭据、连接和运营成本随人员线性增长，也依赖当前无法控制的正式企微资源。本方案不采用。

### 方案 B：只有一个机器人，所有能力都隐藏在内部

优点是接入最简单。缺点是无法体现研究、投资分析等专业助理角色，Agent Team 的协作过程也不够直观。本方案不作为最终产品形态。

### 方案 C：一个统一入口 + 少量公开助理 + 内部 Agent Team

该方案兼顾规模、可维护性和展示效果，因此被选定。公开机器人数量保持稳定，平台内部可继续扩展数字员工；是否为某个内部 Agent 配置公开机器人，不影响它参与任务协作。

## 5. 身份模型

系统区分三类身份，不把它们混成同一个概念：

| 身份 | 例子 | 作用 |
| --- | --- | --- |
| 渠道身份 | `mock-digital-twin` | 决定消息在企微或 Mock 界面中以哪个机器人名称展示 |
| 平台员工身份 | `DT-ZHANGSAN`、`VE-RESEARCH-001` | 保存岗位、权限、知识库、人格和归属关系 |
| Agent 运行身份 | `agent-research-001` | 执行计划、调用工具和继续委派子任务 |

统一入口通过 `from.userid` 完成真人映射：

```text
zhangsan -> 张三 -> 张三数字分身
lisi     -> 李四 -> 李四数字分身
wangwu   -> 王五 -> 王五数字分身
```

相同入口不能意味着共享个人上下文。身份路由完成后，权限、个人记忆、历史任务和会话上下文必须按真人隔离。

## 6. 动态 Agent 角色

“主 Agent”和“SubAgent”是某次任务中的动态角色，不是永久的员工类型：

- 根协调者：接待用户并对最终答复负责的个人数字分身；
- 子任务协调者：接到委派后，在自己的子树中继续拆分任务的 Agent；
- 叶子执行者：直接调用知识库、Skill、Workflow 或插件完成原子任务的 Agent。

例如：

```text
张三数字分身（根协调者）
├── 研究AI员工（子任务协调者）
│   ├── 知识检索Agent（叶子执行者）
│   └── 行业总结Agent（叶子执行者）
└── 投资分析AI员工（子任务协调者）
    ├── 财务计算Agent（叶子执行者）
    └── 风险检查Agent（叶子执行者）
```

默认由根协调者向原始用户返回最终答复。子 Agent 的公开机器人可以展示接单、进度和完成状态，但不直接夺取原始会话的答复责任。

## 7. 总体架构

```text
Swagger / Mock 聊天界面
  │ 企微兼容的文本或文件事件
  ▼
MockWeComBotAdapter
  ├─ 校验和标准化消息
  ├─ msgid 幂等去重
  └─ 转换为统一 ChannelMessage
  ▼
IdentityRouter
  ├─ from.userid -> 真人员工
  └─ 真人员工 -> 个人数字分身
  ▼
RecursiveAgentOrchestrator
  ├─ 创建根任务
  ├─ 按能力选择 Agent
  ├─ 创建子任务和委派记录
  ├─ 控制深度、数量、超时和循环
  └─ 汇总结果
  ▼
Policy -> Gateway / Harness
  ├─ Skill
  ├─ Workflow
  ├─ 知识库
  └─ 插件 / Adapter
  ▼
Task Trace + MockMessageSink
  ├─ Swagger 原始轨迹
  ├─ 前端协作消息
  └─ 最终数字分身答复
```

项目继续遵守现有边界：Agent Team 负责讨论、拆分和分派，真正产生业务副作用的工具调用仍经过 Policy、Gateway 和审计链路。

## 8. 组件边界

### 8.1 `WeComBotAdapter`

提供与渠道无关的统一接口：

- `receive_message`：接收入站文本或文件事件；
- `send_message`：以指定机器人身份产生出站消息；
- `send_progress`：产生任务进度事件；
- `send_file`：产生文件结果事件。

第一期实现 `MockWeComBotAdapter`。以后实现 `RealWeComBotAdapter` 时，Agent Team、身份路由和任务编排接口不变。

### 8.2 `IdentityRouter`

只负责身份解析和访问边界：

1. 根据 `from.userid` 查找平台真人；
2. 查找该真人启用的个人数字分身；
3. 建立或复用对应会话；
4. 返回最小必要的用户、数字分身和权限上下文。

未绑定用户返回明确错误，不自动创建平台员工或数字分身。

第一期不新增身份绑定表，而是在 Demo 配置中显式维护 `mock userid -> HumanEmployee.employee_no` 映射，再通过现有 `DigitalEmployee.source_human_no/owner_human_no` 查找个人数字分身。该映射只用于 Mock，不复用于真实企微凭据绑定。

### 8.3 `AgentCapabilityRegistry`

每个 Agent 声明：

- `agent_id`、显示名称和员工编号；
- 能力列表；
- 可接受的输入类型；
- 数据权限等级；
- 可调用的 Skill、Workflow、知识库和插件；
- 最大并发数和运行状态。

协调者根据能力和权限选择下游，不通过硬编码关键词永久绑定某个 Agent。

### 8.4 `RecursiveAgentOrchestrator`

在现有编排能力上增加递归委派上下文。每个子任务都携带：

```json
{
  "root_task_id": "TASK-1000",
  "task_id": "TASK-1001",
  "parent_task_id": "TASK-1000",
  "trace_id": "TRACE-1000",
  "caller_agent": "DT-ZHANGSAN",
  "assigned_agent": "VE-RESEARCH-001",
  "depth": 1,
  "capability": "industry.research",
  "status": "queued",
  "input": {},
  "constraints": {
    "max_depth": 4,
    "deadline": "2026-08-28T18:00:00+08:00"
  }
}
```

协调者只把完成子任务所需的最小上下文传给下游，不默认共享根会话的完整历史和个人记忆。

### 8.5 `TaskTraceRecorder`

记录答辩和调试所需的可解释轨迹：

- 调用者和被调用者；
- 调用原因和目标能力；
- 输入摘要和输出摘要；
- 调用了 Skill、Workflow、知识库还是插件；
- 开始、完成、失败、超时和取消时间；
- 对应的根任务、父任务和子任务。

轨迹不得保存凭据、文件正文、下载临时地址或其他敏感数据。

## 9. Mock 消息协议

### 9.1 文本入站

建议提供：

```text
POST /api/wecom/mock/messages
```

请求体保持接近企微智能机器人消息：

```json
{
  "msgid": "MSG-001",
  "aibotid": "mock-digital-twin",
  "from": { "userid": "zhangsan" },
  "chatid": "mock-group-001",
  "chattype": "group",
  "msgtype": "text",
  "text": {
    "content": "根据这份材料分析公司是否值得长期投资"
  }
}
```

### 9.2 文件入站

建议提供：

```text
POST /api/wecom/mock/files
```

Swagger 通过 multipart 上传本地文件，Mock 适配器生成标准文件事件和不可猜测的 `file_ref`。Agent 间只传递 `file_ref` 和必要元数据，不传递二进制文件或任意本地路径。

第一期文件类型限制为 `.txt`、`.md`、`.pdf`、`.docx`、`.xlsx`。实施时必须加入大小、扩展名、文件头和压缩包安全检查，不能只根据用户提供的文件名判断类型。Mock 不模拟企微 AES 解密，因此该测试不能作为真实企微文件解密已经完成的证据。

### 9.3 查询任务与轨迹

建议提供：

```text
GET /api/wecom/mock/tasks/{task_id}
GET /api/wecom/mock/tasks/{task_id}/trace
```

任务查询返回状态、子任务树和最终结果；轨迹查询返回每一步 Agent、工具类型、输入输出摘要和时间。

### 9.4 出站消息

Mock 出站消息统一为：

```json
{
  "message_id": "OUT-001",
  "root_task_id": "TASK-1000",
  "sender_bot": "mock-research-agent",
  "sender_name": "研究AI员工",
  "message_type": "progress",
  "content": "行业研究子任务已完成",
  "created_at": "2026-08-28T17:30:00+08:00"
}
```

前端按 `sender_bot` 展示不同机器人头像和名称。

## 10. 任务状态与可靠性

任务状态统一为：

```text
queued -> running -> succeeded
                  -> failed
                  -> input_required
                  -> approval_required
                  -> cancelled
                  -> expired
```

保护规则：

- 最大委派深度为 4；
- 每个 Agent 最多创建 3 个直接子任务；
- 每个根任务最多包含 20 个任务节点；
- 被调用 Agent 不得已经存在于当前祖先路径中；
- 每个任务必须有截止时间和超时状态；
- `msgid` 和任务幂等键防止重复执行；
- 父任务取消时向未结束子任务传播取消；
- 子任务失败时由父 Agent决定重试、降级或向上报告；
- 等待人工审批属于可恢复状态，不占用执行锁；
- Agent 不在等待子任务期间持有独占业务资源。

## 11. 数据持久化策略

### 第一阶段：演示版

不新增数据库表：

- 复用现有 `TaskRun`；
- 将子任务树和调用摘要保存在现有 JSON 字段；
- Mock 机器人和测试用户使用明确标注的 Demo 种子数据；
- 使用由 `aibotid + msgid` 派生的稳定请求键查找现有 `TaskRun`，保证相同 Mock 消息重放时返回原任务而不是重复执行；
- 不使用含义模糊的通用元数据字段隐藏核心业务状态；
- 不写入或修改真实企微凭据。

这样可以用较小改动完成演示，但不承诺跨进程恢复、复杂任务检索和长期审计能力。

### 第二阶段：产品化

真实企微联调和任务模型稳定后，再单独评审是否新增：

- `agent_tasks`：可恢复的任务树；
- `delegation_records`：Agent 间委派记录；
- `task_artifacts`：文件和结果产物；
- `wecom_bot_bindings`：正式机器人绑定和凭据引用。

第二阶段不是第一期 Mock 的隐含范围。

## 12. 数据流示例

用户提交“根据年报分析是否值得长期投资”并附带 PDF：

1. Mock 接口接收 `mock-digital-twin` 消息和文件；
2. `IdentityRouter` 将 `zhangsan` 路由到张三数字分身；
3. 根协调者创建 `TASK-1000`；
4. 根协调者分别委派行业研究和投资分析；
5. 研究 Agent 调用知识检索 Agent，返回行业摘要；
6. 投资分析 Agent 调用文件解析和财务计算能力，返回指标与风险；
7. 两个专业 Agent 以各自 Mock 机器人身份产生进度消息；
8. 根协调者合并结果并生成最终答复；
9. 数字分身 Mock 机器人返回最终文本；
10. Swagger 可查询完整任务树和调用轨迹。

## 13. 错误处理

- 未知 `aibotid`：返回“不支持的 Mock 机器人”，不创建任务；
- 未绑定 `userid`：返回绑定提示，不自动创建员工；
- 重复 `msgid`：返回首次任务状态，不重复调用 Agent；
- 找不到匹配能力：根协调者说明缺少哪个能力；
- 权限不足：记录拒绝原因，不向下游传递敏感上下文；
- 文件不合法：拒绝文件并保留不含正文的审计摘要；
- 子任务超时：父 Agent 可降级汇总已完成结果；
- 循环或超深委派：终止该分支，并在轨迹中标记保护规则；
- 单个子任务失败：不得终止 Mock 服务或其他并行子任务。

## 14. 测试与验收

### 身份测试

1. 张三和李四使用相同入口，分别加载各自数字分身；
2. 张三无法读取李四会话、记忆和文件；
3. 未绑定用户被拒绝。

### 编排测试

1. 根数字分身可调用研究和投资分析 Agent；
2. 研究 Agent 可继续调用知识检索 Agent；
3. 子任务结果能够逐层汇总；
4. 能力不存在、权限不足和子任务失败有明确结果。

### 可靠性测试

1. 深度超过 4 被拒绝；
2. `A -> B -> A` 循环被阻止；
3. 相同 `msgid` 重放不会重复执行；
4. 超时和取消正确传播；
5. 一个子任务失败不影响无依赖的并行子任务。

### 文件测试

1. 允许类型文件能够生成安全 `file_ref` 并被下游读取；
2. 超大、伪造类型和危险压缩包被拒绝；
3. Agent 轨迹中不出现文件正文和任意本地路径。

### 展示测试

1. Swagger 显示完整请求、任务结果和调用轨迹；
2. 前端按不同 Mock 机器人显示接单、进度、完成和最终答复；
3. 每次工具调用明确标注为 Skill、Workflow、知识库或插件；
4. 演示界面明确标注“Mock 企微环境”。

## 15. 实施阶段划分

1. 建立 Mock 企微消息契约和机器人配置；
2. 完成 `from.userid` 到个人数字分身的身份路由；
3. 在现有编排器上增加递归委派上下文；
4. 完成能力注册、权限过滤和下游选择；
5. 记录任务树、调用输入输出和工具类型；
6. 支持 Mock 文件事件和安全文件引用；
7. 加入递归、循环、幂等、超时和取消保护；
8. 提供 Swagger 验证接口、前端协作展示和答辩脚本；
9. 在获得正式机器人资源后，另行设计并验证真实企微适配器。

## 16. 完成定义

第一期只有同时满足以下条件才算完成：

- 一个统一 Mock 数字分身入口可以服务至少两个隔离的测试用户；
- 根 Agent 和至少两个专业 Agent 完成真实的平台内部协作；
- 至少有一个专业 Agent 能继续委派下游 Agent；
- 文本和文件各有一条端到端成功用例；
- 所有调用步骤都能查询输入摘要、输出摘要和调用类型；
- 循环、深度、重复消息、超时和权限测试通过；
- 没有真实企微凭据进入代码、日志或提交；
- 文档和演示中清楚区分 Mock 已验证能力与真实企微待验证能力。
