# 主题：托管智能体（从 harness 能力表拆出）

**这块要回答的问题**：AI员工在哪儿跑、谁来跑、凭据谁管、任务能不能挂到别的机器上跑。

**为什么单独拆出来**：这块的定义还没收敛。官方侧是三种使用端（网页版、桌面版、Python 包）加一批可以远程接的子智能体提供方，但官方文档明确不承诺跨机器的机制、认证和加密。我们侧目前没有对应的实体。先把定义和边界定下来，再排版本。

对照基准：官方 dsh `0.1.5-rc.1` 的智能体、子智能体相关包；平台侧当前 **V0.2**。

---

## 一、官方口径

| 说法 | 内容 |
|---|---|
| 三种使用端 | 网页版（本机 3080）、桌面版、Python 包。都是进程形态，都在本机 |
| 子智能体提供方 | 6 个：进程内两种（spawn、fork），跨进程四种（ACP、Codex、Claude Code、DSH SDK）。按名字注册，一个组合可以并排提供多种 |
| 两种子级 | 一次性的（跑一次给个结果）；可继续的（保留会话、能收后续消息、能中断） |
| 三条输入通道 | 排队下一轮、插入下一步、只注入上下文不唤醒 |
| 待处理队列 | 两级：下一轮、下一步 |
| 停止 | 中止当前活动，可选是否清空待处理。**没有叫「中断」的公开操作，也没有「只中止一步、让整轮继续」的操作** |
| 凭据 | 由使用端托管，官方示例明确不读本地配置目录 |
| 明确不管 | 跨机器的机制、认证、加密；多租户与配额官方未定义 |
| 进程内限制 | 发起方归属只在进程内有效；跨进程、跨重启必须显式传身份。待处理队列不跨进程协调 |

## 二、能力表

| # | 能力项 | 官方对应 | 完成情况 | 成熟度 | 计划版本 |
|---|---|---|---|---|---|
| H1 | 托管形态 | 网页版 / 桌面版 / Python 包 | 一人一容器、无界面一次性调用；没有网页版、桌面版、Python 包形态；容器必须由部署编排预建 | 可用级 | V0.3 |
| H2 | 外部托管智能体接入 | 6 个子智能体提供方，其中 4 个跨进程 | **代码里没有这块**。历史上试过外部协作 worker（AgentTeams），现在只在文档和界面提示里留了名字，业务侧零实现；界面已明说「通用 AgentTeams 等历史实验能力不进入当前有效能力清单」 | 未开始 | V0.5 |
| H3 | 托管凭据 | 使用端托管，不读本地配置目录 | 8 个密钥文件挂进容器；外部系统凭据加密存库；用户级令牌按人存 | 可用级 | V0.3 |
| H4 | 多租户与配额 | 未定义 | 单租户，没有按员工的资源配额 | 未开始 | 暂不排 |
| H5 | 编排与控制面 | 两级待处理队列、三条输入通道、停止可保留待处理、子级优先释放 | 同会话串行靠数据库唯一索引；停一轮靠杀进程；委派有界等待 60 秒；**进程重启后队列不恢复** | 演示级 | V0.5 |

## 三、版本目标

| # | 做什么 |

| # | 做什么 |
|---|---|

## 四、待确认

| # | 问题 |
|---|---|
| 1 | 这个主题的目标是「让 AI员工能在别的机器、别的运行时上干活」，还是「把现在这台的运行方式讲清楚」？两种目标排出来的版本完全不一样 |
| 2 | 如果要接官方的跨进程子智能体，得先定「谁来批、凭据怎么发」。官方明确说这块它不管 |
| 3 | 历史实验（AgentTeams 那条线）是正式废弃，还是留个口子以后重启？现在是「界面明说不用、代码里没有、文档里还提」，三处口径不一致 |
