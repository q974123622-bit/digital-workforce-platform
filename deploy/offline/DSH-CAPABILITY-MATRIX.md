# harness 能力表（对照官方文档 + 版本目标）

一句话用途：把 harness 这块的能力摊成一张表，每项标出现在做到哪、成熟到什么程度、打算在哪个版本收掉。它是排版本的输入，不是需求文档。

**harness 指什么**：AI员工的执行底座，跑模型、跑工具、执行技能的那一层。员工在界面上问一个问题，最后落到这里跑一轮。

对照基准：官方 dsh `0.1.5-rc.1`（官方自己标注技术预览，明说会有破坏性变更、不给版本号和路线图）；平台侧当前 **V0.2**。官方说法取自这个版本包内的中文文档，离线可得，出处见文末。

沙箱、托管智能体两个主题**已从本表拆出**，各自单独成文，不进 harness 的版本目标。

## 一、当前进度（V0.2）

| 项 | 情况 |
|---|---|
| 已经能用 | 员工级容器：一人一个常驻容器，部署时预建 7 个（5 个岗位 AI员工 + 2 个分身）；员工级数据卷，容器内 `/workspace` 和宿主机同一份目录；技能投放；MCP 与技能市场；三个外部 MCP 源 |
| 半成品 | 沙箱（降级当成功返回）、端到端多 agent（只有雏形）、员工分身（本地能跑，还没接企微） |
| 还没有 | 任务级容器、团队级容器、记忆与上下文跟实例剥离、统一的员工身份认证、可查询的记忆 |

容器清单（`compose.yaml` 预建）：

| 类型 | 容器 |
|---|---|
| 岗位 AI员工 | `AI-GENERAL`、`AI-INVESTMENT`、`AI-RESEARCH`、`AI-FUND`、`AI-XYZQ` |
| 员工分身 | `DT-E10281`（张三）、`DT-E20999`（陈晓萌） |

每个容器的挂载：运行版本（只读）、配置档（只读）、`dsh-home`（会话与记忆）、`workspace`（工作区）。**会话和记忆放在每个员工自己的 `dsh-home` 里，跟容器一一对应**，这就是后面要拆开的那一层。

## 二、领导定的五个方向（排版本的输入）

| # | 方向 | 要什么 | 现在做到哪 | 计划版本 |
|---|---|---|---|---|
| 1 | 容器化的 agent | 员工级、任务级、团队级三种粒度。对接 AI老铁 和 CISCClaw。员工级带数据卷、支持多会话、记忆能更新；任务级就是单会话级管理；团队级把员工 ID 换成团队 ID 加权限，共享团队的工作空间和记忆。按员工权限和公共权限访问 MCP、技能、数据文档 | 只做到员工级 | V0.3 定方案，V0.4 落地任务级，V0.6 团队级 |
| 2 | 员工分身 agent | 个人提供自己的分身，接企微，别人能跟这个分身对话；分身只能访问指定的知识库和查询类 MCP，替代本人回答 | 本地已实现，还没接企微 | V0.3 |
| 3 | 端到端 agent | 多 agent 协作，预置不同身份、技能、MCP，协同完成一个完整的 SOP 任务（数仓开发、财富线 SOP、AI员工需求从 jira 到开发到测试到发布） | 只有雏形，协作策略没定 | V0.5 |
| 4 | MCP 和 skill 的目录与分配管理 | 对接中台和公司内部 skillhub，自动发现 MCP 和技能；按用户和管理员分别管理；面向 AI员工动态发现和使用 | 本地已实现。知识库现在按「各 AI员工之间不重叠」分配，界面上展示成独占 | V0.3 |
| 5 | 记忆 | 基于会话的检索，加 Laya 做快速筛选分类，做出可查询、不依赖压缩的 agent 记忆和会话记忆 | 没开始，等武潇部署 Laya 后做实验 | V0.6 |

关于知识库「独占」的澄清（9/23 会上定的）：独占只是**现在的分配规则**，为了防止委派时出问题，默认各 AI员工的知识库不重叠。知识库本质上也是一个 MCP，后续改成跟技能一样——申请、管理员审批、赋予权限，也可以给个命令行工具内置到容器里。

**排序意见**

| 谁 | 意见 |
|---|---|
| 苏柏桦 | 方向 2、4 先做，没有依赖；方向 5 等 Laya 部署后做实验；方向 3 可以比 1 优先，但都要依赖 agent 容器和上下文工程 |
| 陈锋 | 关键是方向 1，先做容器化改造，再按业务需求迭代。个人记忆和上下文数据要跟容器剥离，这事得提前做 |
| 陈锋（短期目标） | 短期就是搞定数字分身、打通 MCP 和统一认证、配套记忆和容器数据卷，让员工能在算力闲时被代理干活，打造几个标杆。分身先只支持两个实例：一个面向他人（限定知识库、明确的问答边界和门禁），一个面向自己（代理干活） |
| 陈锋（多 agent 怎么走） | 倾向于平台任务驱动：流程走到哪一步就唤醒对应实例去干，不为多 agent 单独设计一套逻辑。agent 不脱离已有平台（OA、jira+git+itsm、企微），只是以它自己的身份参与 |

**本表采用的排法**：V0.3 先把方向 2、4 收口（无依赖，能先出效果），同时把方向 1 的改造方案定下来；V0.4 落地容器化改造；V0.5 做方向 3 的标杆；V0.6 做团队级和记忆。如果按「方向 3 优先」走，把 V0.4 和 V0.5 对调即可，但方向 3 仍然要等容器和上下文工程就位。

## 三、怎么读下面这张表

| 列 | 含义 |
|---|---|
| 能力项 | 一行一件事，不拆成任务 |
| 官方对应 | 官方有没有这块、官方叫什么。这列是防重复造的：官方已有的能力，优先想怎么接 |
| 完成情况 | 现在真实做到哪一步，不是计划 |
| 成熟度 | 见下面四档 |
| 计划版本 | 打算在哪个版本收掉；具体做什么看第五节 |

| 档位 | 含义 |
|---|---|
| 未开始 | 只有想法，或只有一个空接口 |
| 演示级 | 能跑通，但靠模拟、降级或单机；没有验收 |
| 可用级 | 真实链路打通，单点能用；缺观测、缺自愈、缺自动化 |
| 生产级 | 有门禁、有验收、可回滚、可观测 |

版本列以后直接往后加（V0.7、V0.8），表结构不用动。

## 六、拆出去的两个主题

| 主题 | 文档 | 为什么拆 |
|---|---|---|
| 沙箱 | `DSH-TOPIC-SANDBOX.md` | 官方定位是「同一台机器上的进程级隔离」，只管文件读写，明确说不用容器；我们走的是容器，两边口径不一样，混在这里会让 harness 的版本目标收不干净 |
| 托管智能体 | `DSH-TOPIC-MANAGED-AGENT.md` | 定义还没收敛。官方是三种使用端加一批远程子智能体提供方，但明确不承诺跨机器的机制、认证和加密 |

两个主题各自维护自己的表和版本目标，不收进本表。

## 七、怎么维护

- 加能力就加一行。行是能力项，不是任务；任务写进 `PLANS.md`。
- 成熟度只在有验收证据时才升档，升档时在提交信息里带上证据位置。
- 「计划版本」列只写版本号，具体做什么补进第五节，并带上对应编号或方向号。
- 「官方对应」这列对不上就说明该重新看官方文档了。官方已有的能力，优先想怎么接，别自己再写一套。
- 领导新给的方向直接加进第二节，再往下拆到第五节的版本目标里。
