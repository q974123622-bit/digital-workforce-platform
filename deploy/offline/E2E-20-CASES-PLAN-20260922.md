# AI员工工作台 · 20 份 case 验收测试方案（2026-09-22）

配套脚本 `deploy/offline/e2e-20-cases.py`，配套结果见 `E2E-20-CASES-REPORT-20260922.md`。

## 一、目标

用 20 份可复现的端到端 case，验证「AI员工工作台」的**业务逻辑正确性**与**系统稳定性**，并且做到：

- 判定不看界面观感，只认运行库里的真源记录，避免「页面看着对」掩盖问题。
- 失败能定位到根因，能区分「平台缺陷」与「模型偶发」。
- 换一台机器（含堡垒机）能原样重跑，不引入任何新依赖。

## 二、范围

**覆盖**：知识库检索与授权边界、数字分身委派与引用透传、技能路由、会话操作（就地编辑重跑）、兴证e家员工服务 MCP 按人鉴权、缺参补全链路、市场申请与管理员审批、并发与争用、重复提交、中途停止、超长输入、错误凭据、越权与未登录、容器重启恢复。

**不覆盖**：群聊协作（按本轮口径排除）、前端渲染与交互（另由前端单测覆盖）、性能压测与容量评估。

## 四、判定原则

1. **按本次 execution_id 精确等待**。`GET /conversations/{cid}/runs/latest` 在本次执行被整体回滚时会回落到上一次执行，只看「latest 是不是终态」会把失败判成通过。
2. **断言只读真源**，不读界面：

| 判据 | 真源 |
| --- | --- |
| 执行终态、错误码 | `agent_execution.status / error_code / trigger_message_seq` |
| 轨迹事件（补全、技能路由） | `agent_execution_event` |
| 知识库读授权、外部 MCP 调用、补全提交 | `audit_event`（`action=read` 的 allow/deny + `knowledge_base_id`） |
| 委派链路 | `delegation_run` |
| 引用卡片、作废标记 | `conversation_message.tool_cards / superseded_at` |
| 待补全记录与掩码 | `tool_input_request` |
| 按人凭据 | `mcp_user_credential`（只读掩码） |

3. **「不 5xx」优先于「必须 200」**。越权、超长输入、错误凭据的合法结果可能是 401/403/404/409/422，语义对就算过；出现 5xx 一律判失败。
4. **并发按争用资源加锁**。同一会话有活跃执行时再提交返回 409（唯一索引 `uq_agent_execution_active_conversation`）；同一个 AI 员工的 harness 任务同一时刻只能跑一个，委派目标是同一个时后到者要排队。锁键 `emp:<发起员工>` / `delegate:<委派目标>`，重叠串行、不重叠才并行。故意制造争用的 case 显式不吃锁，并放到隔离阶段单独跑。
5. **偶发与缺陷分开**。平台只把「AI员工执行失败，可稍后重试」写进 `error_message`，dsh 的原始报错只在服务端日志里。脚本按 trace 从 backend 容器日志抓 `harness execution failed ... detail=...`，命中模型侧非法 JSON 的记 `FLAKY`（重试 1 次，仍失败也不计入缺陷），否则才是 FAIL。
6. **越权断言用真实文档名**。未授权库的「真实文档名」不手写，从历史审计的 `result_summary.documents[].title` 自动取，避免拿过期文档名做断言。

## 六、执行方式

```bash
cd deploy/offline

# 全量（推荐并发度 3：避免打爆模型网关、降低 409 概率）
nohup python3 e2e-20-cases.py --workers 3 \
  --report ops/logs/e2e-20-cases-$(date +%Y%m%d).json \
  --report-md ops/logs/e2e-20-cases-$(date +%Y%m%d).md \
  > ops/logs/e2e-20-cases-$(date +%Y%m%d).log 2>&1 &

# 只跑某几个 case（定位用）
python3 e2e-20-cases.py --only L11 S06 --workers 1

# 跳过会写数据的 case（市场审批、错误凭据）
python3 e2e-20-cases.py --no-mutate
```

耗时参考：逐 case 耗时合计约 14 分钟，并发度 3 时墙钟约 7 分钟。必须后台跑（本机长命令会被自动跳过）。

## 九、已知前提与坑

1. `/run/user/0` 不存在时 `docker exec` 直接失败，backend 启动同步 harness 安全 profile 会跟着失败并 crash-loop，看起来像平台挂了。
2. 签名密钥由容器 entrypoint 导出给 uvicorn，`docker exec` 不继承容器创建后的环境变量，容器内另起进程铸令牌必然 401，要从 `/run/secrets/harness_signing_secret` 自己读一次。
3. 平台错误信封是 `{"error":{"code","message","detail":{...}}}`，不是 `{"detail":...}`；`retryable` 在 `error.detail` 里。
4. 会话的 `/clear` 会连带删掉该会话的执行与消息（`generation` 自增），不能靠它做「按 trace 反查历史」。
5. 同一 AI 员工的 harness 任务并发时是**有界排队**（`delegation_slot_wait_seconds` 默认 60 秒），不是立刻 409；所以「同一目标并发争用」这类 case，排队后成功和直接 409 两种结果都算通过。
